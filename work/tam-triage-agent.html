01The brief

A procurement-software company gets support tickets that need fast, consistent triage. Build an agent that handles one ticket at a time and does what a Technical Account Manager would: understand the customer, check the context, find the right policy, and decide what happens next.

The data was realistic and messy: roughly 3,000 tickets, 200 accounts and 390 knowledge-base articles, with some tickets missing their account_id.

02Agent, not pipeline

The key requirement: the LLM chooses which tools to call, in whatever order the ticket needs, instead of running a fixed sequence. A ticket with a known account skips the lookup, while a vague one may need several knowledge-base searches.

  1. Resolve the accountEven when account_id is blank, using the other signals in the ticket.
  2. Gather contextTier, renewal date, usage trend, past escalations and related tickets.
  3. Retrieve knowledgeRelevant KB articles, including the support policy.
  4. DecideCategory, priority, routing, escalation, whether to notify the TAM, duplicate status and whether to ask for clarification.
  5. WriteA customer reply, an internal note and a step-by-step reasoning trace.

03Design decisions

  • Schema-locked output: every decision is returned in a fixed schema, so downstream systems can trust the shape of the result.
  • Provider-agnostic LLM client: runs on Ollama (local and free), Anthropic or OpenAI, configured through a .env file.
  • Reasoning trace for every step: a support lead can see why the agent escalated a ticket, not just that it did.
  • Clean package layout: data loaders, LLM client, schema and agent are separate modules, with validation scripts alongside.
